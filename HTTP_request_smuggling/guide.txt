# HTTP Request Smuggling Educational Lab

## 1. Objective

Build a completely local, Docker-based educational laboratory demonstrating the mechanics of:

1. HTTP Request Smuggling — CL.TE
2. HTTP Request Smuggling — TE.CL

The lab must allow the user to send raw HTTP/1.1 requests through a deliberately vulnerable frontend proxy to a deliberately vulnerable backend server.

The critical educational objective is to make the difference between frontend and backend HTTP request parsing visible.

The implementation must NOT rely on production HTTP reverse proxies or frameworks whose normal behavior automatically rejects or normalizes ambiguous `Content-Length` + `Transfer-Encoding` requests.

This is an intentionally vulnerable toy environment for localhost use only.

---

# 2. Required architecture

Create two completely independent Docker Compose environments.

## CL.TE

Host:

```text
http://localhost:8080
```

Architecture:

```text
Client
  |
  | HTTP/1.1
  v
CL.TE Frontend :8080
  |
  | persistent TCP connection
  v
CL.TE Backend
```

The frontend must determine request boundaries using:

```text
Content-Length
```

The backend must determine request boundaries using:

```text
Transfer-Encoding: chunked
```

Therefore:

```text
Frontend = CL
Backend  = TE
```

Use:

* Docker Compose
* Python 3.12+

* Raw TCP sockets for the vulnerable HTTP parsing components

Do NOT use:

* Flask
* FastAPI
* Django
* Express
* Node HTTP server
* Nginx
* Apache

```python

```

# 6. HTTP parser requirements

The implementation must explicitly separate:

## HTTP request headers

Parse:

```text
METHOD SP PATH SP HTTP/VERSION
```

and headers.

Header names should be treated case-insensitively.

At minimum support:

```text
Host
Content-Length
Transfer-Encoding
Connection
Content-Type
```

Unknown headers should be preserved.

Do not automatically normalize away duplicate or conflicting framing headers.

---

# 7. CL.TE frontend behavior

The CL.TE frontend must:

1. Accept a raw TCP connection from the client.
2. Read the request headers.
3. Parse `Content-Length`.
4. Read exactly `Content-Length` bytes following the header terminator.
5. Treat those bytes as the complete request body.
6. Forward the resulting raw request bytes to the backend.
7. Keep the backend TCP connection persistent.
8. Continue parsing subsequent client requests on the same connection.

The frontend should NOT use `Transfer-Encoding` to determine the body boundary.

Conceptually:

```python
if content_length is present:
    body = recv_exact(content_length)
```

Even if:

```text
Transfer-Encoding: chunked
```

is present.

---

# 8. CL.TE backend behavior

The CL.TE backend must:

1. Accept the persistent TCP connection from the frontend.
2. Parse request headers.
3. If:

```text
Transfer-Encoding: chunked
```

is present, ignore `Content-Length`.
4. Parse the body using HTTP/1.1 chunked encoding.
5. Stop at:

```text
0\r\n
```

followed by the terminating CRLF/trailers as appropriate.
6. Immediately attempt to parse any remaining bytes in the TCP stream as the beginning of another HTTP request.

This behavior intentionally creates the CL.TE desynchronization.

---

# 9. TE.CL frontend behavior

The TE.CL frontend must:

1. Accept raw TCP connections.
2. Parse:

```text
Transfer-Encoding: chunked
```

3. Decode the chunked body.
4. Forward the complete request downstream.
5. Keep the backend TCP connection persistent.
6. Ignore Content-Length when determining the frontend request boundary.

Conceptually:

```python
if transfer_encoding == "chunked":
    body = read_chunked_body()
```

---

# 10. TE.CL backend behavior

The TE.CL backend must:

1. Parse request headers.
2. Ignore `Transfer-Encoding` when determining request boundaries.
3. Use:

```text
Content-Length
```

to determine the body length.
4. Read exactly that number of bytes.
5. Treat all remaining bytes in the TCP stream as the beginning of another request.

This intentionally creates TE.CL desynchronization.

---

# 11. IMPORTANT: persistent connections

This is mandatory.

Do NOT create a new backend TCP connection for every request.

The vulnerability depends on the frontend and backend disagreeing about where requests end on the same TCP byte stream.

Therefore:

```text
Client
   |
   | Request A + Request B bytes
   v
Frontend
   |
   | same TCP stream
   v
Backend
```

The backend must be able to process:

```text
Request A
Request B
Request C
...
```

from one persistent connection.

The logs should make it possible to directly compare:

```text

        VS

```


or equivalent.

Example usage:


The client must:

2. Send the exact file bytes.
3. Keep the connection open long enough to receive responses.

# 21. Testing requirements

Write automated tests for both labs.

The tests must verify:

## CL.TE

The backend receives more than one logical request from a single client TCP stream when the intentionally crafted payload is sent.

Verify through backend logs or a test endpoint.

## TE.CL

Likewise verify that a single client connection causes the backend to parse the smuggled bytes as another request.

Tests should fail if:

* frontend and backend use the same framing rules
* backend connection is not persistent
* the frontend consumes too many/few bytes
* the backend does not attempt to parse remaining bytes
* chunked parsing is incorrect

# 25. Implementation quality

Keep the code intentionally simple and heavily commented.

This is a cybersecurity university laboratory, not production software.

Every important parser operation should explain:

```text
What bytes are being consumed?
Why are they being consumed?
Which HTTP rule is being followed?
What does the other parser believe?
```

Avoid abstracting the parser behind large frameworks.

A student should be able to open:

```text
frontend.py
backend.py
```

and understand the complete CL.TE/TE.CL mechanism.
